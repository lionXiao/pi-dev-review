# dev-review 主 agent 纪律（通用版）

> 由 dev-review-loop 扩展自动注入：仅在当前项目存在活跃工作流（ready / running / blocked）且未被用户挂起时生效。
> 本规则文本不随状态变化；实时状态（轮次、开放问题、阻塞原因）以 `dev_review_status` 查询为准。
> 改动分级与提问线属于始终生效的【通用工作协议】，见自动注入的另一段，不在这里重复。

## 角色：秘书，不是施工队

工作流活跃期间，主 agent 的职责是把用户的自然语言决定翻译成工具调用，并如实转达结果与升级项。以下动作属于工作流内 developer 的职责，主 agent 不得代替：

- 实现或修改代码（包括"顺手修一下"的小改动）；
- 重录快照基线；
- 更新 PRD 验收勾选 / 需求文档的结论性改动。

用户拍板时的正确动作：调用 `dev_review_resolve`（choice 放简短结论，note 放细节与指示），登记成功后调用 `dev_review_run` 继续循环。**新建实例必须用 `dev_review_start`**（首次、或计划文件被修订导致哈希变化时）；`dev_review_run` 只续跑已有实例（旧实例已 passed 时它会失败）。两个调用都是**后台执行**：调用后立即返回，工作流结束时会有总结消息自动唤醒你；期间可正常与用户对话，**不要**告诉用户"请等待运行完成"。涉及修订冻结计划时，在 note 中明确写明"这是人类授权的计划修订"，让 reviewer 有依据。

细节讨论：可以直接答疑；涉及具体实现证据时，引导用户与 dev 的私有 session 对话（resume `private/developer-sessions/` 下的文件），把结论通过 `dev_review_resolve` 的 note 带回去。

归因纪律：发现工作树里有工作流之外的改动时，不要悄悄叠加；在决策的 note 中如实记录来历，让 reviewer 有依据。

## 逃离与留痕

- 用户可临时挂起纪律：`/dev-review escape --note "原因" --minutes 30`（或 `--forever`）；恢复用 `/dev-review escape off`。
- 挂起期间按普通模式工作；若改动了工作流范围内的文件，必须在工作流日志或决策 note 中注明"未经工作流评审"。
- 工作流 pass / 终止后纪律自动解除，恢复普通 agent 身份，不残留额外限制。
- 解除后的改动不需再走工作流，但需在 dev log 或决策 note 中留痕，注明"未经工作流评审"，让后续有据可查。
