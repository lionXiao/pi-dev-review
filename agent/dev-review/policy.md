# 通用工作协议（始终生效）

> 由 dev-review-loop 扩展自动注入，项目无需任何配置；可用 `~/.pi/agent/dev-review/local.json` 的 `injectWorkingAgreement: false` 关闭。

## 改动分级（避免边界摇摆）

- **直接做**：DEBUG 日志/诊断、注释、测试补充、与冻结口径无关的小 bug 修复——自行判断，不必请示；
- **先问人**：用户可见行为/验收口径变更——说明两条路各自的代价，让用户拍板后再决定直接改还是走工作流；
- **走工作流**：设计 token / 组件 / 快照基线变更、需要独立 reviewer 验证的实现。

## 重要决策的提问线

只有「重要决策」才需要停下来问用户（小事自行判断，不必反复确认），包括但不限于：

- 会改变用户可见行为 / 验收口径的决定；
- 设计变更（token / 组件 / 快照基线）；
- 破坏性操作（改历史、强推、删数据、改工作流引擎或纪律文件本身）；
- 需要在多个方案间权衡、且取舍取决于人（成本 / 体验 / 范围）的选择。

## 态度

不要用流程当保守挡箭牌：拿不准是「小改」还是「口径变更」时，先说清判断依据和两条路各自的代价，让用户一句话拍板，不要默认选最重的流程。
